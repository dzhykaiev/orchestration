# ADR-001: Initial Architecture

**Status:** Accepted
**Date:** 2026-03-01

## Context

We need to build an AI-driven software orchestration platform that accepts high-level goals and produces working code using multiple AI agents working in parallel.

## Decision

TypeScript monorepo with event-driven orchestration using BullMQ/Redis and PostgreSQL.

### Components

| Component | Technology | Responsibility |
|-----------|-----------|----------------|
| API Server | Fastify | REST API, validation, job enqueueing |
| Orchestrator | BullMQ workers | Agent coordination, task dispatching |
| Dashboard | Next.js | Progress tracking, project management |
| Database | PostgreSQL + Drizzle | Persistent state |
| Queues | BullMQ + Redis | Job orchestration, retries |
| Shared | TypeScript package | Types, schemas, utilities |

### Key Decisions

1. **Monorepo over microservices** — single codebase, shared types, simpler deployment
2. **BullMQ over custom queue** — battle-tested, priorities, retries, progress tracking
3. **PostgreSQL over document store** — structured data with JSONB flexibility
4. **Fastify over Express** — TypeScript-first, faster, built-in validation
5. **Next.js for dashboard** — rapid development, SSR, React ecosystem
6. **Single process orchestrator** — agents are functions, not services

## Alternatives Considered

### Microservices

Each agent as a separate service with message broker. Rejected because:
- Excessive complexity for MVP
- Coordination overhead
- Harder to debug

### Monolithic Threading

Single process with thread-based parallelism. Rejected because:
- No built-in retry/priority
- Hard to scale later
- No job persistence

### Serverless

Each agent as a Lambda/Cloud Function. Rejected because:
- Cold start latency for LLM calls
- Complex local development
- Vendor lock-in

## Consequences

- Simple local development (Docker Compose + pnpm dev)
- Shared types prevent interface drift
- Single codebase to maintain
- Limited horizontal scaling (acceptable for MVP)
